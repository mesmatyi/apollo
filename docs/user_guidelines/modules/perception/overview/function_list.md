# Function List

Apollo alpha further divides the modules by function, so that each component is more focused and the corresponding modules can be selected for optimization and upgrade as needed. The overall directory description is as follows:

| Component                     | Function Overview |
| :---------------------------- | :---------------- |
| camera_detection_2d           | The camera 2D object detection module is a multi-task model developed based on yolo that can simultaneously output dozens of dimensions of information, such as 2D, 3D, and vehicle turn signals. This module performs image data preprocessing, detection, result postprocessing, and other operations. |
| camera_detection_3d           | The camera 3D object detection module includes two models, caddn and smoke, and can output 2D and 3D information at the same time. This module performs image data preprocessing, detection, result postprocessing, and other operations. This module can pass its results directly to the camera_tracking component. |
| camera_detection_bev          | The BEV object detection module is a multi-camera transformer model trained on the Nuscenes dataset under the paddlepaddle framework, which can perform inference on data from multiple cameras to obtain obstacle targets. |
| camera_location_estimation    | This module can calculate the rotation angle of an object in the camera coordinate system from the 2D bounding box information, 3D observation angle information, 3D size information predicted by the network, and the camera intrinsic parameters. Then, combined with obstacle size templates, this module solves for the object's 3D bbox and converts the coordinates to the world coordinate system. |
| camera_location_refinement    | Postprocesses the obstacles detected in the previous stage. It mainly fits the ground plane to the camera plane to calculate the relative position and height of the tuned object with respect to the camera. |
| camera_motion_service         | This module provides the current motion estimation. |
| camera_overlap_filter         | The camera overlap filter module is used to fuse the detection results of multiple cameras. |
| camera_tracking               | The camera tracking module uses the omt obstacle tracker to process the obstacles detected by the camera and outputs the tracked obstacles for subsequent multi-sensor fusion. |
| lane_detection                | The lane detection module detects lane lines through camera sensors. Lane lines can be used as an aid for other modules. |
| lidar_detection               | Performs 3D object detection based on point clouds and outputs the position, size, and orientation of the detected objects. Apollo provides 4 LiDAR detection models: centerpoint, maskpillars, pointpillars, cnnseg. |
| lidar_detection_filter        | Filters foreground and background objects according to object attributes, lane lines, ROI, and so on. |
| lidar_tracking                | The tracking module is used to track the motion trajectories of obstacles, update their motion state and geometry, and assign tracking IDs. |
| multi_sensor_fusion           | The multi-sensor fusion module fuses the output results of multiple sensors (LiDAR, camera, radar), making detection results more reliable. This module uses postprocessing technology, and the algorithm adopted is probabilistic fusion. |
| pointcloud_ground_detection   | Point cloud ground detection: detects ground points and saves the indices of all non-ground points. |
| pointcloud_map_based_roi      | Filters out point clouds outside the ROI.<br>The region of interest (ROI) specifies the drivable area, including the road surface and intersections retrieved from the HD map. The HDMap ROI filter processes LiDAR points outside the ROI and removes background objects, such as buildings and trees around the road. What remains is the point cloud inside the ROI for subsequent processing.<br>Given an HDMap, the membership of each LiDAR point indicates whether it is inside or outside the ROI. Each LiDAR point can be queried through a 2D quantized lookup table (LUT) of the area around the vehicle. |
| pointcloud_preprocess         | The point cloud preprocessing module preprocesses the point cloud data output by the driver. It removes outlier points, points that are too far, points scanned on the ego vehicle itself, and points that are too high. |
| radar_detection               | The radar detection module detects and tracks obstacles through radar sensors, and then sends them to the multi-sensor fusion module. |
| traffic_light_detection       | After the projection in the preprocessing stage, a projection box is obtained on the image, but the projection box is not entirely reliable, so a larger region of interest (ROI) is calculated from the projected position of the signal light and used to determine the exact bounding box of the signal. Signal light detection (Detect) is a traditional convolutional neural network detection task that takes an image with ROI information as input data and outputs bounding boxes in sequence. |
| traffic_light_recognition     | The purpose of the traffic light recognition module is to recognize the color of the traffic light. This task is completed using a traditional convolutional neural network. The input of the recognition module is an image with ROI information and a set of bounding box information, and the output is a four-dimensional vector representing the probability that each bounding box is black, red, yellow, and green respectively. If and only if the probability is large enough, the category with the highest probability is recognized as the state of the signal light. Otherwise, the signal light state is set to Unknown, indicating that the state is undetermined. |
| traffic_light_region_proposal | This module is used to query localization and draw signal light information, select the camera used for traffic light detection according to the projection of the signal light on the image plane, and finally save the camera selection result. |
| traffic_light_tracking        | In the recognition stage, the output state may not be the true state due to occlusion or traffic light flicker, so the corresponding results should be corrected. |
| common                        | Common library |
| msg_adapter                   | The msg adapter module is used to forward messages inside the perception module.<br>The channel names of internal messages usually contain an internal field "inner". These messages are only passed between threads, not between processes, so you cannot use "cyber_monitor" to view them. Because these messages are generally large, such as images and point cloud data, to avoid copying, serialization, and deserialization, we pass objects directly, so these messages can only be passed within a thread.<br>For ease of debugging, you can use the msg adapter module to forward messages so that they can be viewed through cyber_monitor. |
| tools                         | Some offline debugging tools, including lidar, camera, and trafficlight |
