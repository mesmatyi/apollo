Starting with Apollo 9.0, we bring you the monocular two-stage vision detector yolox+yolo3d. Compared with the monocular vision yolo model in earlier versions, this release includes a good deal of exploration and optimization in implementation approach, training code and model deployment. To help everyone carry out secondary development of algorithms on this framework faster and better, this article takes the yolox model as an example to show users how to add a vision detection model for the 2D object detection task in the new version of Apollo.

## 1. Training Data Preparation

### Dataset Introduction

The KITTI dataset is a dataset for autonomous driving research jointly sponsored by the Karlsruhe Institute of Technology in Germany and the Toyota Technological Institute at Chicago. It provides benchmarks for various tasks such as optical flow, object detection and depth estimation. The training code that Apollo open-sources later will all use open-source data as the training data, and users can then quickly iterate by adapting their own data.

### KITTI Data Download

We provide trainable code based on KITTI data. For the parts of training that involve data conversion, we also provide the relevant conversion tools to help everyone adapt quickly and minimize tedious operations for developers in later development.

[KITTI data official website link](https://www.cvlibs.net/datasets/kitti/): download the vision-related data and extract it.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_a897c75.png)

We generally store the data in the following form, which is also the general form commonly used:

```bash
├── data
│   └── KITTI
│       ├── calib       # Calibration files
│       ├── images_2    # Image data
│       └── labels_2    # Annotation data
```

### Analysis of Difficult Points in the Dataset

#### Coordinate System

In the KITTI dataset, the vision data coordinate system is "right-down-front", that is, the positive x axis points right, the positive y axis points down, and the positive z axis points forward. If you annotate data yourself, note that coordinates need to be converted from the lidar coordinate system to the camera coordinate system.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_29cb9f8.png)

#### Object Categories

The 8 common data categories in KITTI data are: Car, Van, Truck, Pedestrian, Person_sitting, Cyclist, Tram, Misc. Developers can later modify the labels according to their own data.

#### Data Annotation Format

KITTI-type data looks as follows. The annotation result of one object is described with 15 values:

```bash
Car 0.00 0 1.85 387.63 181.54 423.81 203.12 1.67 1.87 3.69 -16.53 2.39 58.49 1.57
```

| Data Type  | Meaning                                                                                                                                  | kitti index | kitti position |
|:----------:|:----------------------------------------------------------------------------------------------------------------------------------------:| ----------- |:--------------:|
| type       | Object type                                                                                                                              | 0           | 1              |
| truncated  | Degree of truncation, referring to pixels missing for objects at the edge of the image because they are cut off by the capture frame    | 1           | 2              |
| occluded   | Degree of occlusion, referring to occlusion caused by multiple obstacles overlapping along the line of sight                              | 2           | 3              |
| alpha      | Observation angle: the angle between the line from the vehicle position to the camera center and the x axis [which direction the object is in relative to the ego vehicle] [straight ahead is -PI/2, right is 0] | 3 | 4 |
| 3dbox-h    | Height                                                                                                                                   | 8           | 9              |
| 3dbox-w    | Width                                                                                                                                    | 9           | 10             |
| 3dbox-l    | Length                                                                                                                                   | 10          | 11             |
| location-x | Center position x, positive toward the right of the vehicle body                                                                         | 11          | 12             |
| location-y | y, positive toward the bottom of the vehicle body [can be considered 0 under the planar assumption]                                      | 12          | 13             |
| location-z | z, positive toward the front of the vehicle body                                                                                         | 13          | 14             |
| ry         | Rotation angle: the angle between the heading of the target vehicle and the x axis of the ego vehicle [which way the object is going] [straight ahead is -PI/2, right is 0] | 14 | 15 |

For the two angles ry and alpha, refer to the explanation shown in the figure below:

ry describes "the angle between the heading of the target vehicle and the x axis of the ego vehicle". That is, while the ego vehicle is driving straight, vehicles on the left and right driving straight ahead have the same ry value of -PI/2. Look at the bird's-eye view to get a feel for it: vehicle 1 on the left is driving to the left rear, with alpha>0 and the absolute value of alpha greater than ry; vehicle 2 on the right is driving straight ahead, with alpha<0 and the absolute value of alpha greater than ry. Think about why that is.

## 2. Introduction to Vision Perception Components

Vision perception currently includes three algorithm components: camera_detection_bev, camera_detection_multi_stage and camera_detection_single_stage.

### Perception Components Overview

The current perception module components are listed below:

| Component Name                | Meaning                                                              |
| ----------------------------- | -------------------------------------------------------------------- |
| camera_detection_bev          | Perception bev algorithm detector                                    |
| camera_detection_multi_stage  | Perception end-to-end algorithm detector                             |
| camera_detection_single_stage | Perception multi-stage algorithm detector                            |
| camera_detection_occupancy    | Perception bev+occ algorithm detector                                |
| camera_location_estimation    | Pose and position information of objects detected by the camera      |
| camera_location_refinement    | Tuning of the pose and position information of objects detected by the camera |
| camera_tracking               | Target feature matching and tracking based on camera features        |
| msg_adapter [common module]   | Converts the perception output messages and sends them to cyber_monitor |

### Starting the Perception Components

We start the yolox3d algorithm through the launch file at the following path:

```bash
modules/perception/launch/perception_camera_multi_stage.launch
```

This launch file contains all the task steps the algorithm needs to execute, presented in the form of dags:

```bash
# Output the camera detection results to /apollo/perception/obstacles, for detection result message conversion and publishing
<dag_conf>/apollo/modules/perception/msg_adapter/dag/msg_adapter.dag</dag_conf>
# yolox3d two-stage detection
<dag_conf>/apollo/modules/perception/camera_detection_multi_stage/dag/camera_detection_multi_stage_yolox3d.dag</dag_conf>
# Depth estimation based on geometric methods
<dag_conf>/apollo/modules/perception/camera_location_estimation/dag/camera_location_estimation.dag</dag_conf>
<dag_conf>/apollo/modules/perception/camera_location_refinement/dag/camera_location_refinement.dag</dag_conf>
# Target feature matching and tracking based on camera features
<dag_conf>/apollo/modules/perception/camera_tracking/dag/camera_tracking.dag</dag_conf>
```

For developers: if you are researching 2D vision algorithms and want to further tune detection results on 2D detection based on your own data, you can replace the yolox model in the perception_camera_multi_stage component for your own iteration; if you are researching 3D end-to-end perception algorithms, you can develop in the camera_detection_single_stage component, such as the existing algorithms like SMOKE.

### Adding a New 2D Object Detection Algorithm

The camera_detection_multi_stage component is shown below. To add a new detection algorithm, the /conf, /dag, /data and /detector folders need to be modified. You can refer to the implementation of yolox3d and modify accordingly:

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_b2ced7c.png)

```bash
├── camera_detection_multi_stage // camera detect 2d module
    ├── conf                     // module configuration files
    ├── dag                      // dag files
    ├── data                     // model params
    ├── detector                 // main part for detector
    │   ├── yolox3d              // Yolox3dObstacleDetector
    │   └── ...                  // You can use your own detector！
    ├── interface                // function interface folder
    ├── proto                    // proto files
    ├── camera_detection_multi_stage_component.cc // component interface
    ├── camera_detection_multi_stage_component.h
    ├── cyberfile.xml            // package management profile
    ├── README.md
    └── BUILD
```

The roles of the corresponding folders are briefly summarized as follows:

| Folder    | Meaning                                                                                  |
| --------- | ---------------------------------------------------------------------------------------- |
| /dag      | Sets the conf file path                                                                  |
| /conf     | Sets camera_name, detection algorithm name, configuration file, and the image message input channel |
| /data     | All parameter configuration information used by the detection algorithm, which can be modified in proto |
| /detector | Pre- and post-processing and inference implementation of the detection algorithm        |

## 3. Training Code Modification and Model Iteration

### Introduction to the Perception Multi-Stage Task

The multi-stage task flow is shown below. Stage1 and stage2 each use a separate model. In the first stage we use a 2D detection model to box the foreground targets of people and vehicles, and then in stage2 we perform 3D pose regression on these two kinds of targets individually. Below, taking the stage1 task as an example, I will describe how to add a vision detection model for the 2D object detection task.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_43bcb4a.png)

### Model Selection

2D object detection algorithms have become very mature today, and in 2023 notable ones such as yolov8 and RT-DETR drew a lot of attention from developers. These algorithms have made many optimizations in detection performance and real-time inference after deployment. However, considering the open-source license requirements of the apollo code itself, we ultimately chose the yolox algorithm for the monocular vision multi-stage task camera_detection_multi_stage. This algorithm also performs well after being trained with road test data, so the yolox model is used as the example here.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_6fbedfd.png)

Let us add a new detector to this component by training a yolox model!

### Code Download

The yolox training code adapted for Apollo can be found in the [ApolloAuto open-source repository](https://github.com/ApolloAuto):

```bash
git clone https://github.com/ApolloAuto/apollo-model-yolox.git
```

### Training Code Modification

Because Apollo's camera_tracking component needs to obtain part of the feature maps after convolution for the subsequent tracking module, we need to make some modifications to the original yolox code so that it outputs part of the network's intermediate results during model inference. The relevant modifications can be found in the following files:

- yolox/models/darknet.py returns the outputs["dark2"] feature map in the forward pass

- yolox/models/yolo_pafpn.py returns apollo_feature in the forward pass

- yolox/models/yolox.py also returns apollo_feature in the forward pass

## 4. Model Deployment and Implementation of the Pre- and Post-Processing Modules

Model deployment is the most important part. How to actually use an onnx-type model in the detection module is the key step. We will use the onnx model exported by the training code above for inference.

### Perception Algorithm Parameter Configuration

When using it, the inference framework can be Onnx or PyTorch; the output sizes must correspond one-to-one with the exported model; other hyperparameter configuration can be added as appropriate according to the needs of the code.

Model configuration file path: modules/perception/camera_detection_multi_stage/data/yolox3d.pb.txt.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_face3ac.png)

### Create the Algorithm Component: Yolox3DObstacleDetector

Add your own detector, Yolox3DObstacleDetector, by inheriting from the BaseObstacleDetector base class. In this detector we must implement two functions:

- Init() // The initialization function loads the configuration parameters in /data and calls the ONNX inference framework to initialize the model input and output blob addresses,

- Detect() // Maintains the CameraFrame data, performs preprocessing, model inference and data postprocessing on the received images, and adds obstacle information to frame->detected_objects.

### Complete the Algorithm Initialization Function: Init()

Here config_file and model_info correspond to the model configuration parameters in the /conf file path and the /data file path respectively. Once both are filled in correctly, the inference framework initialization function is called to initialize the inference framework. Here we choose the ONNX framework; for other models you can also choose the PyTorch framework.

```bash
if (!InitNetwork(model_info, model_path)) {
AERROR << "Init network failed!";
return false;
}
net_->Infer();
```

### Complete the Detection Algorithm Interface: Detect()

In `modules/perception/camera_detection_multi_stage/camera_detection_multi_stage_component.cc`, the whole algorithm is invoked through this interface, so the overall 2D and 3D detection pipeline needs to be completed in this function.

### Image Preprocessing: Preprocess()

Before data is fed into the network for inference, it must be consistent with the data in the training code. The yolox data preprocessing part is as follows; we just need to imitate it to complete the c++ image preprocessing:

```bash
def preproc(img, input_size, swap=(2, 0, 1)):
    if len(img.shape) == 3:
        padded_img = np.ones((input_size[0], input_size[1], 3), dtype=np.uint8) * 114
    else:
        padded_img = np.ones(input_size, dtype=np.uint8) * 114
    r = min(input_size[0] / img.shape[0], input_size[1] / img.shape[1])
    resized_img = cv2.resize(
        img,
        (int(img.shape[1] * r), int(img.shape[0] * r)),
        interpolation=cv2.INTER_LINEAR,
    ).astype(np.uint8)
    padded_img[: int(img.shape[0] * r), : int(img.shape[1] * r)] = resized_img

    padded_img = padded_img.transpose(swap)
    padded_img = np.ascontiguousarray(padded_img, dtype=np.float32)
    return padded_img, r
```
