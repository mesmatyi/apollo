## Feature Overview

### Feature Overview

The Perception module plays a vital role in the autonomous driving system. The functions of its sub-modules are implemented with three kinds of sensors: lidar, radar and camera. Each sensor performs object recognition and tracking tasks, and finally fusion fuses the data from the sensors. In addition, the camera also implements lane line recognition and traffic light detection. The task pipeline of each sensor is roughly similar: preprocessing, recognition, filtering, tracking.

In an autonomous driving system, the perception module is mainly responsible for recognizing obstacles around the vehicle as well as traffic signs, so the quality of the perception algorithms directly affects the safety of autonomous driving, and how to iterate on perception algorithms faster becomes the key. In Apollo alpha, the perception module has been refactored into components and offers multiple development modes. When the existing functionality fully meets the user's development needs, no code needs to be developed, and the functional requirements of the scenario can be met by modifying component configuration or model parameters. For component development, when the user's scenario needs to introduce new requirements and work together with other components to complete a task, such as adding a lidar background segmentation function, you only need to complete the corresponding development while satisfying the upstream and downstream message channel subscription and publishing. For plugin development, for example, in the lidar object detection obstacle filtering component we provide two filtering plugin methods; if they cannot meet the user's needs, the user can develop a corresponding filtering plugin following the provided plugin development documentation. Through plugin development, developers can focus more on the algorithm itself without paying too much attention to the framework implementation.

### Running Flow

The Apollo autonomous driving platform takes the HD map and the localization module as its core. The other modules are built on these two. The perception module recognizes the environment around the autonomous vehicle, and the collection, processing and analysis of environment information and in-vehicle information, that is, environment perception, is the foundation and prerequisite for autonomous driving of intelligent vehicles. The perception results are passed to the subsequent modules for use.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_760538e.png)

### Framework Design

In the original perception framework, the lidar, camera, radar and fusion parts were defined in four modules. The internal functions of the lidar and camera modules were complex, with a high learning cost. After the perception framework was split, the module dependencies are clear. The lidar and camera perception pipelines are divided into multiple modules with linear dependencies; the radar and fusion functions are within single modules, with functions as shown in the diagram. Under the new perception framework, the lidar and camera modules are more lightweight than before, which is more conducive to secondary development. Each component can be started and debugged independently.

### Feature List

Apollo has further divided the modules by function so that the function of each component is more focused, making it convenient to select the corresponding modules for optimization and upgrade as needed. The following is the overall directory description:

| Component                     | Function Overview                                                                                                                                                                                                                |
|:-----------------------------:|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------:|
| camera_detection_multi_stage  | The camera 2D object detection module is a multi-task model developed based on yolo that can output dozens of kinds of information simultaneously. This module completes operations such as image data preprocessing, detection, and result postprocessing. |
| camera_detection_single_stage | The camera 3D object detection module includes two models, caddn and smoke, and can output 2D and 3D information simultaneously. This module completes operations such as image data preprocessing, detection, and result postprocessing. This module can pass results directly to the camera_tracking component. |
| camera_detection_bev          | The BEV object detection module is a multi-camera transformer model trained on the Nuscenes dataset under the paddlepaddle framework, and can run inference on the data of multiple cameras to obtain obstacle targets. |
| camera_detection_occupancy    | The BEV+OCC detection module is a multi-camera transformer model trained on the Nuscenes dataset under the pytorch framework, and can perform BEV obstacle detection and occupancy grid detection. |
| camera_location_estimation    | This module can calculate the rotation angle of a target in the camera coordinate system from the 2D bounding box information, 3D observation angle information, 3D size information and camera intrinsic parameters predicted by the network, then combine them with the obstacle size template to solve the target's 3D bbox and convert the coordinates to the world coordinate system. |
| camera_location_refinement    | Postprocesses the obstacles detected in the previous stage. Mainly, it calculates the relative position and height of the tuned target to the camera by fitting the ground plane to the camera plane. |
| camera_motion_service         | This module provides current motion estimation.                                                                                                                                                                                  |
| camera_overlap_filter         | The camera overlap filter module is used to fuse the detection results of multiple cameras.                                                                                                                                      |
| camera_tracking               | The function of the camera tracking module is to use the omt obstacle tracker to process the obstacles detected by the camera, and output the tracked obstacles for subsequent multi-sensor fusion. |
| lane_detection                | The lane detection module detects lane lines through the camera sensor. Lane lines can be used as an aid to other modules.                                                                                                       |
| lidar_detection               | Performs 3D object detection based on point clouds and outputs the position, size and orientation of the detected objects. Apollo provides 4 lidar detection models: centerpoint, maskpillars, pointpillars, cnnseg. |
| lidar_detection_filter        | Filters foreground and background objects according to object attributes, lane lines, ROI, etc.                                                                                                                                  |
| lidar_tracking                | The tracking module is used to track the motion trajectories of obstacles, update the motion state and geometric shape of obstacles, and assign tracking ids. |
| multi_sensor_fusion           | The multi-sensor fusion module fuses the output results of multiple sensors (Lidar, Camera, Radar) to make the detection results more reliable. This module uses postprocessing techniques, and the algorithm adopted is probabilistic fusion. |
| pointcloud_ground_detection   | Point cloud ground detection: detects ground points and saves the indices of all non-ground points.                                                                                                                              |
| pointcloud_map_based_roi      | Filters out the point cloud outside the ROI. The region of interest (ROI) specifies the drivable area, including the road surface and intersections retrieved from the HD map. The HDMap ROI filter processes lidar points outside the ROI and removes background objects such as buildings and trees around the road. What remains is the point cloud in the ROI for subsequent processing. Given an HDMap, the membership of each LiDAR point indicates whether it is inside or outside the ROI. Each LiDAR point can be queried through a 2D quantized lookup table (LUT) of the area around the car. |
| pointcloud_preprocess         | The point cloud preprocessing module preprocesses the point cloud data output by the driver. It removes out-of-range points, points that are too far, points scanned on the ego vehicle itself, and points that are too high. |
| radar_detection               | The radar detection module detects and tracks obstacles through the radar sensor and then sends them to the multi-sensor fusion module.                                                                                          |
| traffic_light_detection       | After the earlier projection in the preprocessing stage, a projection box is obtained on the image, but the obtained projection box is not completely reliable, so a larger region of interest (ROI) is calculated from the projected signal light position, used to determine the exact bounding box of the signal light. Signal light detection (Detect) is a traditional convolutional neural network detection task, which takes an image with ROI information as input data and outputs bounding boxes in turn. |
| traffic_light_recognition     | The purpose of the traffic light recognition module is to recognize the color of the traffic light. This task is completed using a traditional convolutional neural network. The input of the recognition module is an image with ROI information and a set of bounding box information, and the output is a four-dimensional vector representing the probability that each bounding box is black, red, yellow and green. If and only if the probability is large enough, the category with the highest probability is recognized as the state of the signal light; otherwise the signal light state is set to Unknown, indicating that the state is undetermined. |
| traffic_light_region_proposal | This module is used to query localization and draw traffic light information, select the camera used to detect traffic lights according to the projection of the traffic lights on the image plane, and finally save the camera selection result. |
| traffic_light_tracking        | In the recognition stage, due to occlusion or traffic light flickering and other reasons, the output state may not be the true state, so the corresponding results should be corrected. |
| common                        | Common library                                                                                                                                                                                                                   |
| msg_adapter                   | The msg adapter module is used to forward messages inside the perception module. The channel names of internal messages usually contain an internal field "inner". These messages are only passed between threads, not between processes, so users cannot use "cyber_monitor" to view them. Because these messages are generally large, such as images and point cloud data, to avoid copying, serialization and deserialization, we pass objects directly, so these messages can only be passed within a thread. For convenience of debugging, the msg adapter module can be used to forward messages so that they can be viewed through cyber_monitor. |
| tools                         | Some offline debugging tools, including lidar, camera and trafficlight                                                                                                                                                           |

## Module Overview

Currently Apollo uses components that are used on demand. At the same time, to make extension convenient, for example replacing a model, plugins are used to add new models.

- Green represents the parts that users often need to replace, where new algorithms or functions need to be developed. Based on the original framework, you only need to replace the part you want to replace, without paying attention to message flow and the framework.

- Blue represents the parts that users do not need to replace often. The module integrates all the algorithms and its function is a whole, and functionality is modified directly through configuration. If you want to replace it, you can write a new component.

### Lidar Detection Flow

Lidar detection is used for 3D object detection. Its input is the lidar point cloud, and its output is the type and coordinates of the detected objects. The three components developers pay the most attention to are pointcloud_map_based_roi, lidar_detection and lidar_detection_filter. pointcloud_map_based_roi involves the relevant roi filtering rules, and the lidar_detection component covers the model deployment related content in the object detection process. Apollo and paddle3d have connected the whole pipeline from model training to deployment into apollo, and later practice courses will also cover this. The Apollo lidar perception module provides 4 object detection models, and developers can select different detectors according to the configuration file to verify the detection results. With the latest algorithm plugins, developers can focus more on the algorithm itself without paying too much attention to the framework implementation. The lidar_detection_filter component handles detected obstacle filtering related functions. Lidar tracking is used to track the 3D target objects detected above. Its input is the lidar point cloud detection result, and its output is the ID of the tracked object.

### Camera Detection Flow

In the camera detection flow, developers focus on the camera_detection_multi_stage, camera_detection_single_stage and camera_tracking components. The camera_detection_multi_stage and camera_detection_single_stage components involve 2D and 3D model deployment, preprocessing and other functions, and developers can replace models and develop related functions as needed. The functionality in camera_tracking is fairly integral, and developers can modify the configuration items in the component for the corresponding tracking strategy. The camera_detection_multi_stage detection flow outputs 2D bounding boxes; compared with the camera_detection_single_stage component, which outputs 3D detection results directly, it has an additional process of converting 2D information into 3D obstacle information.

![image.png](./camera目标检测.png)

### Fusion Flow

The multi-sensor fusion module fuses the detection results of multiple sensors. Its input is the lidar, camera and radar detection target results, and its output is the fused result. The roles of several important base classes are listed here: BaseFusionSystem is equivalent to the entry of the fusion module and initializes the ProbabilisticFusion probabilistic fusion algorithm; BaseTracker updates the state of tracked trajectories; BaseGatekeeper is used to decide whether to publish tracked obstacles to the final channel.
