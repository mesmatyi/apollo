LiDAR and cameras are currently the two most important sensors in autonomous driving. Because LiDAR ranging is accurate, the accuracy of obstacles detected by LiDAR is generally higher than that of cameras.

LiDAR (Laser Radar, abbreviated as LiDAR) is a sensor that uses laser beams to detect characteristic quantities such as target position and reflection intensity. It consists of a laser transmitter, an optical receiver, a turntable and an information processing system. The laser converts electrical pulses into light pulses and emits them, and the optical receiver then restores the light pulses reflected from the target back into electrical pulses and sends them to a display.

Compared with traditional radar, LiDAR has advantages such as high resolution, high precision and strong resistance to active interference. Its working principle is to use the wavelength and pulse width of the laser, and measure distance accurately by measuring the propagation time of light. The transmitting system of a LiDAR has a very small aperture and a narrow receiving area, so the probability that a deliberately transmitted laser jamming signal enters the receiver is extremely low.

According to differences in the scanning system, LiDAR can be divided into mechanical, hybrid solid-state (rotating mirror, prism, MEMS mirror), solid-state (FLASH, OPA) and so on. According to differences in the ranging method, it can be divided into TOF LiDAR and FMCW LiDAR.

## Overall Framework of LiDAR Perception

Apollo's LiDAR perception consists of the following components, which work together to implement the LiDAR perception function.

![Overall Framework of LiDAR Perception.jpeg](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/%E6%BF%80%E5%85%89%E9%9B%B7%E8%BE%BE%E6%84%9F%E7%9F%A5%E6%95%B4%E4%BD%93%E6%A1%86%E6%9E%B6_ae57744.jpeg)

Before introducing each module, we first need to know the inputs and outputs of the LiDAR perception module, and how it works.

Inputs of the LiDAR perception module:

- LiDAR point cloud. Generated by the LiDAR sensor, obtained by scanning the surrounding environment as a series of points and reflection intensity values. The subscribed message channel is `/apollo/sensor/lidar16/compensator/PointCloud2`,

- Coordinate transformation. The detected obstacles are in the LiDAR coordinate system and need to be converted into the world coordinate system, so the transformation from the LiDAR to world coordinates is required. The subscribed message channels are `/tf and /tf_static`.

Outputs of the LiDAR perception module:

- Obstacle information. Obstacle information detected from the point cloud, including target category, size, speed and tracking ID, used by the downstream planning module for path planning. The published message channel is `/apollo/perception/obstacles`.

  ![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_90de77a.png)

Next, we introduce these modules in detail.

### Point Cloud Preprocessing (pointcloud_preprocess)

Point cloud preprocessing is the first component of LiDAR perception. Its main functions are as follows:

- Filter invalid points, that is, filter points whose coordinates are nan

- Filter points whose height exceeds z_threshold. For example, filter points higher than 6 meters.

- Points passing through the ego vehicle: considering the LiDAR installation position, the LiDAR may scan the vehicle itself, so points on the vehicle itself are filtered out to avoid mistaking them for obstacles.

### HD Map Filtering (pointcloud_map_based_roi)

Filters out the point cloud outside the ROI.

The region of interest (ROI) specifies the drivable area, including the road surface and intersections retrieved from the HD map. The HDMap ROI filter processes the lidar points outside the ROI and removes background objects such as buildings and trees around the road. What remains is the point cloud within the ROI for subsequent processing.

### Ground Detection (pointcloud_ground_detection)

Finds the ground. The purpose of finding the ground is mainly for subsequent point cloud segmentation.

![Ground Detection.gif](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/%E5%9C%B0%E9%9D%A2%E6%A3%80%E6%B5%8B_4d2a947.gif)

### 3D Object Detection (lidar_detection)

Using deep learning algorithms, object detection is performed on the point cloud processed above, finally obtaining the position and speed information of pedestrians, vehicles and non-motorized vehicles in the current scene.

Apollo currently supports the following 4 LiDAR object detection models.

- **center_point_detection**: an anchor-free 3D object detection algorithm based on point clouds, with certain advantages in computational efficiency and accuracy. Its core idea is to perform object detection and position regression by predicting the center point of objects, without needing to pre-generate a large number of candidate boxes (anchors).

- **cnn_segmentation**: an in-house model.

- **mask_pillars_detection**: an in-house model, with some improvements made on top of point_pillars.

- **point_pillars_detection**: a 3D object detection model for autonomous driving, based on point cloud data. The model converts point cloud data into a pillar-shaped sparse representation, and then combines a 2D CNN and a 3D SSD to perform object detection.

The online inference frameworks currently supported are:

- pytorch

- paddle

- onnx

- TensorRT

The model whose training code has been opened is the center_point LiDAR detection model; how to train and deploy the model will be covered later.

### Detection Result Filtering (lidar_detection_filter)

Filters the foreground and background obstacles detected by the model according to object attributes, lane lines, ROI and so on.

### Object Tracking (lidar_tracking)

Tracks the detected obstacles to obtain the speed and tracking ID of targets, used for subsequent target trajectory prediction.

### Message Forwarding (msg_adapter)

The msg adapter module is used to forward messages inside the perception module.

The channel names of internal messages usually contain an internal field "inner". These messages are only passed between threads, not between processes, so you cannot use cyber_monitor to view them. Because these messages are generally large, such as images and point cloud data, we pass objects directly to avoid copying, serialization and deserialization, so these messages can only be passed within a thread.

For convenience of debugging, the msg adapter module can be used to forward messages so that they can be viewed through cyber_monitor. Moreover, pure LiDAR perception does not need sensor fusion, so messages need to be forwarded and output through the msg_adapter module. If there is a multi-sensor fusion module, you need to start the LiDAR, camera and millimeter-wave radar modules plus the fusion module to output the final perception results.

## LiDAR Perception Parameter Introduction

Next we introduce the first perception development mode: modifying the parameters of the LiDAR perception module.

### Parameter Directory Structure

First, the configuration directory of each component is introduced, using the LiDAR detection module as an example

```bash
├── lidar_detection
    ├── conf            // Component configuration files
    ├── dag             // Component dag files
    ├── data            // Function configuration files
    ├── detector
    │   ├── center_point_detection
    │   ├── cnn_segmentation
    │   ├── mask_pillars_detection
    │   └── point_pillars_detection
    ├── interface
    ├── proto
    ├── lidar_detection_component.cc
    ├── lidar_detection_component.h
    ├── cyberfile.xml   // Package configuration file
    ├── README.md
    └── BUILD
```

Common configuration directory: the common configuration shared by multiple components is placed under the `modules/perception/data` path.

```bash
modules/perception/data
├── BUILD
├── conf    // Common perception configuration, e.g. some singletons
├── cyberfile.xml
├── flag    // All gflags of the perception module passed in on the command line, used by dag
├── models  // Model storage path
└── params  // Sensor intrinsics and extrinsics
```

### 4. Modify Parameters

1. Modify the model output confidence

   By adjusting the model output confidence, learn how to adjust the detection results output by the model. The higher the model's confidence threshold, the more accurate the detection results, but the lower the recall; the lower the confidence threshold, the higher the recall and the lower the precision. Therefore precision and recall need to be balanced to achieve a good result.

   First check whether the configuration in `/apollo/modules/perception/lidar_detection/conf/lidar_detection_config.pb.txt` is CenterPointDetection:

   ```bash
   plugin_param {
      name: "CenterPointDetection"
      config_path: "perception/lidar_detection/data"
      config_file: "center_point_param.pb.txt"
    }
   ```

   Then modify `score_threshold` in `/apollo/modules/perception/lidar_detection/data/center_point_param.pb.txt`.

   ```bash
       postprocess {
     score_threshold: 0.25      // Detection result confidence
     num_output_box_feature: 7
     bottom_enlarge_height: 0.1  // 0.25 -> 0.1
     top_enlarge_height: 0.25
     width_enlarge_value: 0
     length_enlarge_value: 0
   }
   ```

   ![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_ba00a57.png)

2. Modify the ROI range

   Modifying the ROI parameters can filter out, by rules, obstacles that do not need attention, avoiding interference with the autonomous vehicle.

   Find the `/apollo/modules/perception/lidar_detection_filter/data/roi_boundary_filter.pb.txt` file and modify the parameters

   ```bash
   distance_to_boundary_threshold: 0.0
   confidence_threshold: 0.0
   cross_roi_threshold: 0.6
   inside_threshold: -1.0
   ```

   ![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_66d8cfb.png)
