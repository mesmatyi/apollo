# Package Management Tutorial - Basic Concepts and Building Custom Components and Plugins

Prerequisites

Before reading this document, make sure you have followed the [Package Management Installation](../安装指南/包管理安装方式.md) document to finish installing the Apollo environment management tool and the container environment

## Overview

This tutorial covers the basics of using package management to download, install, and build Apollo modules. You will set up a workspace and build a simple C++ project that illustrates the key concepts of package management in Apollo, such as the .workspace.json and .env files. After completing this tutorial, see [Apollo Development Tool - buildtool](../框架设计/命令行工具/buildtool.md) to learn about the advanced usage of buildtool, the key tool in package management.

In this tutorial, you will learn:

- The configuration information newly added in Apollo's package management mode
- Creating a simple example component, then compiling and running it
- Installing the source code of an existing package into the workspace, modifying it, and compiling it
- How to bring a third-party library into the workspace and depend on it
- Packaging a module you have developed further and deploying it to another host

## Before You Begin

In package management mode, Apollo organizes and manages packages in terms of `projects`. Apollo officially provides several example projects, which can be found on Apollo's GitHub homepage. In this tutorial, we use the `application-pnc` project. You can obtain the example project from Apollo's GitHub repository:

```shell
git clone https://github.com/ApolloAuto/application-pnc.git
```

This project declares dependencies on pnc-related packages. By deploying it, you can quickly debug and simulate Apollo's pnc packages. The directory structure of the project is as follows:

```shell
application-pnc
├── .workspace.json
├── .env
├── WORKSPACE
├── core
│   ├── BUILD
│   └── cyberfile.xml
└── profiles
    └── default
```

As you can see, this project contains no Apollo source code, only some configuration files (.workspace.json and .env) and the core module. Next, we will deploy this project and introduce the concepts mentioned above step by step.

## Deploying application-pnc

Before deploying the whole project, you need to have some understanding of the files in the workspace. The workspace, that is, the whole project directory, stores the module source code. It also contains some special files recognized by the Apollo compilation toolchain:

`WORKSPACE`: This is the WORKSPACE file in bazel. It identifies the directory and its contents as a Bazel workspace and is located at the root of the project directory structure. Unless you need to additionally introduce third-party libraries recognizable by bazel, this file generally does not need to be modified.

`.workspace.json`: This file is also located at the root of the project. It indicates where the project's packages are downloaded from, as well as the package version. Its content is as follows:

```json
{ "repositories": [{ "name": "apollo-core", "version": "9.0.0-alpha2-r28" }] }
```

The `repositories` field contains the package repository information, and `name` is the name of the package repository. Currently, Apollo has two repositories for users to choose from:

- apollo-core: All package repositories of the Apollo open-source code base (X86 architecture)
- apollo-core-arm: All package repositories of the Apollo open-source code base (ARM architecture)

And `version` is the package version downloaded for this project.

When you want to upgrade the whole project from version `9.0.0-alpha2-r28` to version `9.0.0-alpha2-r29`, simply change the file to the following content:

```json
{ "repositories": [{ "name": "apollo-core", "version": "9.0.0-alpha2-r29" }] }
```

Then redeploy the project, and the packages the project depends on will be automatically upgraded to version `9.0.0-alpha2-r29`.

> Note: Because the external interfaces of Apollo modules may change between versions, the project's source code may need additional adaptation work after upgrading the version

`.env`: Apollo currently still needs to run in a docker container. This file specifies the repository and tag of the image used when starting the container. Its content is as follows:

```shell
APOLLO_ENV_NAME=pnc
APOLLO_ENV_WORKLOCAL=1
APOLLO_ENV_CONTAINER_REPO='registry.baidubce.com/apollo/apollo-env-gpu'
APOLLO_ENV_CONTAINER_TAG='9.0-latest'
```

Where:

- `APOLLO_ENV_NAME` specifies the name of the container. In actual development, multiple Apollo projects are often started in one development environment. Configuring this variable solves the problem of conflicting container names.
- `APOLLO_ENV_CONTAINER_REPO` specifies the image repository
- `APOLLO_ENV_CONTAINER_TAG` specifies the tag of the image

Besides the files mentioned above, the project also includes the "source code" of the `core` module under the `core` path, although this module does not include any source code in the traditional c++ sense.

In Apollo's package management mode, the source code of a module includes the following:

- `cyberfile.xml` (required): The description file of the module, which describes the module's name, its path in the workspace, its dependencies, version information, and so on
- `BUILD` (required): The bazel BUILD file, which describes in what form the c++ source code, python source code, configuration files, data files, etc. in the module should be organized for compilation
- A series of source code, data files, configuration files, etc. (optional)

Next, we take the core module as an example to briefly introduce the source files involved in a module

Some of the more important attributes are:

- name: The name of the module.
- version: The module version number. Since this is local source code, the version is local.
- type: The type of the module, which must be module.
- src_path: The path of the module's source code in the workspace.
- depend: The dependencies of the module. The depend tag has some attributes:
  - repo_name: The same as the name of the dependent module.
  - type: In what form the dependency is introduced, with src and binary as options. src introduces the dependency as source code, that is, the compilation toolchain copies the dependency's source code into the workspace and compiles it together; binary introduces the dependency in binary form, that is, when compiling the current module, the compilation toolchain imports the dependent module's dynamic libraries and header files for compilation.
- builder: The underlying compilation tool; currently only bazel is supported.

### Understanding BUILD

The BUILD file is bazel's BUILD file. It tells Bazel how to compile the required outputs, such as executable binaries or libraries.

In package management mode, Apollo provides some macros and rules on top of bazel, for example in core's BUILD file

```python
load("//tools:apollo_package.bzl", "apollo_package")

package(default_visibility = ["//visibility:public"])

apollo_package()
```

Here `apollo_package` is a macro newly added in package management mode. In package management mode, this macro must be added to the BUILD files of all module source code to ensure that the module source code can be compiled and deployed normally.

In addition, Apollo provides corresponding rules for c++ source code, python source code, and proto source code, for example in the BUILD file of the `cyber` source code:

```python
load("//tools:apollo_package.bzl", "apollo_cc_library", "apollo_package")

apollo_cc_library(
    name = "cyber_state",
    srcs = ["state.cc",],
    hdrs = ["state.h",],
    deps = ["//cyber/common:cyber_common",],
)
```

In package management mode, please use the rules provided by Apollo, which are:

- apollo_cc_library: Declares that the target generates a dynamic library, replacing bazel's native cc_library
- apollo_cc_binary: Declares that the target generates an executable, replacing bazel's native cc_binary
- apollo_cc_test: Declares that the target generates a test executable, replacing bazel's native cc_test
- apollo_component: Declares that the target generates an Apollo component
- apollo_plugin: Declares that the target generates an Apollo plugin

The apollo_cc_library, apollo_cc_binary, and apollo_cc_test rules are used in the same way as bazel's native rules.

How to use the two newly added rules, apollo_component and apollo_plugin, is introduced below.

#### Installing Source Code into the Workspace

Besides deployment, developers may want to view or modify the source code of a module or plugin. A module can be installed with the following command:

```shell
buildtool install planning-task-lane-follow-path
```

This command installs the source code of `planning-task-lane-follow-path` into the workspace. The source code can be found under `modules/planning/planning_base/tasks/lane_follow_path`.

You can modify the code above to change the behavior of the task, and then compile it to make the changes take effect.

```shell
buildtool build -p modules/planning/
```

The above command compiles all modules under the `modules/planning` path.

Then restart planning through `dreamview`, or rerun planning from the command line, for further debugging.

When you want to discard the local compilation results and restore the original behavior of `planning-task-lane-follow-path`, you can reinstall the module with the following command:

```shell
rm -f modules/planning/planning_base/tasks/lane_follow_path && buildtool reinstall planning-task-lane-follow-path
```

Then restart planning.

|-- dag

Where:

- BUILD: Tells bazel how to compile this component
- conf: Stores the configuration files of the component. The content of sample_component.pb.txt is parsed into the SampleComponentConfig type defined by sample_component.proto; sample_component.conf declares some gflags
- dag, launch: Store the startup files of the component
- proto: Stores the proto message definitions of the component's configuration and messages
- c++ source code: Describes the initialization of the component and its behavior when it receives the corresponding message

This example component listens on the `/apollo/sample_component` channel and prints the corresponding message in the terminal after receiving a message.

Because this example is a component, the apollo_component rule is used in the BUILD file:

```python
apollo_component(
    name = "libsample_component_component.so",
    srcs = [
        "sample_component.cc",
    ],
    hdrs = [
        "sample_component.h",
    ],
    deps = [
        "//cyber",
        "//sample_component/proto:sample_component_proto",
    ],
)
```

The apollo_component rule declares that the target is a component, where:

- name: The name of the dynamic library produced by the component, consistent with the dynamic library name read in the dag file
- srcs: The source files of the component
- hdrs: The header files of the component
- deps: The dependencies of the component. Here it depends on the cyber interfaces and the target declared under the component's own proto

This example can be compiled directly:

```shell
buildtool build -p sample_component
```

After compilation completes, simply run it:

```shell
mainboard -d sample_component/dag/sample_component.dag
```

You can also modify the component's initialization and its behavior upon receiving messages, and simply compile after modifying the code

#### Creating an Apollo Plugin

As with components, you can use the buildtool create command to create a plugin:

```shell
buildtool create --template plugin --base_class_name apollo::planning::Task sample_plugin --dependencies planning
```

> A plugin needs to inherit from a plugin base class. The --base_class_name parameter in the above command declares inheriting the Task class in planning, sample_plugin declares the source path of the plugin, and the --dependencies parameter adds a dependency on planning in cyberfile.xml

A sample_plugin directory is added to the workspace:

```shell
sample_plugin/
|-- BUILD
|-- conf
|   `-- sample_plugin.pb.txt
|-- cyberfile.xml
|-- plugin_sample_plugin_description.xml
|-- proto
|   |-- BUILD
|   `-- sample_plugin.proto
|-- sample_plugin.cc
`-- sample_plugin.h
```

Compared with a component, a plugin adds a description file `plugin_sample_plugin_description.xml`:

```xml
<library path="sample_plugin/libsample_plugin.so">
    <class type="apollo::SamplePlugin" base_class="apollo::planning::Task"></class>
</library>
```

This file describes the name of the plugin's dynamic library, as well as the plugin's class name and the name of the base class it inherits, so that cyber can load the plugin correctly.

Unlike components, because the definitions of plugin base classes differ, the plugin template created by the above command is only a most basic template that cannot be compiled directly. Developers need to fill in the corresponding information before it can be compiled. The information that developers need to fill in is introduced below.

##### Included Header Files

In the create command, the base class to inherit is specified as apollo::planning::Task, but in fact sample_plugin.h merely inherits apollo::planning::Task and does not include the corresponding header file:

```c++
#pragma once

#include <memory>
#include "cyber/plugin_manager/plugin_manager.h"

namespace apollo {

class SamplePlugin : public apollo::planning::Task {
 public:
  bool Init();
};

CYBER_PLUGIN_MANAGER_REGISTER_PLUGIN(apollo::SamplePlugin, apollo::planning::Task)

} // namespace apollo
```

Developers can refer to planning's interface documentation to add the header file corresponding to `apollo::planning::Task`, and modify the function signatures according to the base class definition:

```c++
#pragma once

#include <memory>
#include "cyber/plugin_manager/plugin_manager.h"
#include "modules/planning/planning_base/task_base/task.h"

namespace apollo {

class SamplePlugin : public apollo::planning::Task {
 public:
  bool Init(const std::string &config_dir, const std::string &name,
            const std::shared_ptr<apollo::planning::DependencyInjector> &injector) override;

  apollo::common::Status Execute(apollo::planning::Frame *frame,
    apollo::planning::ReferenceLineInfo *reference_line_info) override;
};

CYBER_PLUGIN_MANAGER_REGISTER_PLUGIN(apollo::SamplePlugin, apollo::planning::Task)

} // namespace apollo
```

##### Modifying the Source Implementation File

Since the function signatures were modified, the corresponding implementation also needs to be modified accordingly. The following is the cc file initialized by the create command:

```c++
#include <memory>
#include "sample_plugin/sample_plugin.h"

namespace apollo {

bool SamplePlugin::Init() {
  return true;
}

} // namespace apollo
```

The modified cc file:

```c++
#include <memory>
#include "sample_plugin/sample_plugin.h"

namespace apollo {

bool SamplePlugin::Init(const std::string &config_dir, const std::string &name,
            const std::shared_ptr<apollo::planning::DependencyInjector> &injector) {
  return true;
}

apollo::common::Status SamplePlugin::Execute(apollo::planning::Frame *frame,
        apollo::planning::ReferenceLineInfo *reference_line_info) {
    apollo::planning::Task::Execute(frame, reference_line_info);
    return apollo::common::Status::OK();
}

} // namespace apollo
```

##### Modifying the BUILD File to Add Dependent Targets

Likewise, the plugin's BUILD file itself does not include the target corresponding to the base class. Developers can refer to the BUILD file of the dependent module to add the target corresponding to the header file

The following is the BUILD file initialized by the create command:

```python
load("//tools:apollo.bzl", "cyber_plugin_description")
load("//tools:apollo_package.bzl", "apollo_cc_library", "apollo_package", "apollo_plugin")
load("//tools:cpplint.bzl", "cpplint")

package(default_visibility = ["//visibility:public"])

filegroup(
    name = "sample_plugin_files",
    srcs = glob([
        "conf/**",
    ]),
)

apollo_plugin(
    name = "libsample_plugin.so",
    srcs = [
        "sample_plugin.cc",
    ],
    hdrs = [
        "sample_plugin.h",
    ],
    description = ":plugin_sample_plugin_description.xml",
    deps = [
        "//cyber",
        "//sample_plugin/proto:sample_plugin_proto",

    ],
)

apollo_package()
```

The target corresponding to `apollo::planning::Task` is `"//modules/planning/planning_base:apollo_planning_planning_base"`, so after modifying the `BUILD` file:

```python
load("//tools:apollo.bzl", "cyber_plugin_description")
load("//tools:apollo_package.bzl", "apollo_cc_library", "apollo_package", "apollo_plugin")
load("//tools:cpplint.bzl", "cpplint")

package(default_visibility = ["//visibility:public"])

filegroup(
    name = "sample_plugin_files",
    srcs = glob([
        "conf/**",
    ]),
)

apollo_plugin(
    name = "libsample_plugin.so",
    srcs = [
        "sample_plugin.cc",
    ],
    hdrs = [
        "sample_plugin.h",
    ],
    description = ":plugin_sample_plugin_description.xml",
    deps = [
        "//cyber",
        "//sample_plugin/proto:sample_plugin_proto",
        "//modules/planning/planning_base:apollo_planning_planning_base",
    ],
)

apollo_package()
```

This BUILD file uses the apollo_plugin rule to declare that the target generates a plugin, where:

- name: The name of the dynamic library produced by the component, consistent with the dynamic library name read in the plugin description file
- description: The name of the plugin description file
- srcs: The source files of the component
- hdrs: The header files of the component
- deps: The dependencies of the component. Here it depends on the cyber interfaces and the target declared under the component's own proto

After the modification, you can compile with the following command:

```shell
buildtool build -p sample_plugin
```

After compilation, the plugin can be loaded and used by the planning component. The plugin compiled by following the above steps is only an empty plugin and has no behavior of its own. To make the plugin plan vehicle trajectories, you need to further write the corresponding business code. In addition, for the plugin to be loaded and called by planning, planning's configuration files need to be modified; for details, refer to planning's getting-started tutorial, which is not elaborated here.

#### Introducing Third-Party Libraries into the Workspace

So far, apollo supports introducing the following types of third-party libraries:

- Third-party libraries that can be downloaded through apt
- Third-party libraries that exist as source code
- Third-party libraries that exist as header files and dynamic libraries

For the first type of third-party library, simply add a depend tag in the `cyberfile.xml` of the module that needs to depend on the library. Suppose your module depends on the `curl` library; add the following dependency information in `cyberfile.xml`:

```xml
<depend>libcurl4-openssl-dev</depend>
```

Then add the dynamic library to be linked in the module's BUILD file:

```python
apollo_cc_library(
    name = "sample_lib",
    srcs = [
        "sample.cc",
    ],
    hdrs = [
        "sample.h",
    ],
    copts = STUDIO_CONNECTOR_COPTS,
    linkopts = ["-lcurl"],
)
```

Add the corresponding "#include" in the source file:

```c
#include <curl/curl.h>
```

The second type of third-party library is essentially no different from a third-party library developed by the user in the workspace and can be treated as an ordinary module. That is, the user writes the `cyberfile.xml` and `BUILD` files for it, and it can be compiled and used normally.

The third type of third-party library is handled similarly to the second type and can also be treated as an ordinary module, but when writing the `BUILD` file, an additional declaration is needed for the dynamic library, for example the following cancard driver:

```shell
can_card
|-- BUILD
|-- cyberfile.xml
|-- include
|   `-- bcan.h
`-- lib
    `-- libbcan.so
```

In `cyberfile.xml`, you need to depend on the packages bazel-extend-tools, 3rd-bazel-skylib, and 3rd-gpus:

```xml
<package format="2">
  <name>can-card</name>
  <version>local</version>
  <description>
    cancard Lib.
  </description>

  <maintainer email="apollo-support@baidu.com">Apollo</maintainer>
  <license>Apache License 2.0</license>

  <type>module</type>
  <depend>bazel-extend-tools</depend>
  <depend expose="False">3rd-bazel-skylib</depend>
  <depend expose="False">3rd-gpus</depend>
  <src_path url="https://github.com/ApolloAuto/apollo">//can_card</src_path>

</package>
```

In `BUILD`, the dynamic library needs to be declared using the native `cc_library`:
```python
load("//tools:apollo_package.bzl", "apollo_package", "apollo_cc_binary", "apollo_cc_library")

package(
    default_visibility = ["//visibility:public"],
)

native.cc_library(                  # Declare the dynamic library of this third-party library using bazel's native cc_library rule
    name = "bcan",
    srcs = ["lib/libbcan.so"],
    tags = ["shared_library"],      # Mark this type as a third-party dynamic library
    hdrs = ["include/bcan.h"],
)

apollo_cc_library(                  # Create an apollo_cc_library so that other modules can depend on this target
    name = "sample_can",
    deps = [":bcan"]                
)

apollo_package()
```

For a module that needs to depend on this third-party library, `cyberfile.xml` needs to add the dependency on that library:
```xml
<depend type="binary" repo_name="can-card">can-card</depend>
```

In the `BUILD` file, simply depend directly on the apollo_cc_library declared for that third-party library:
```python
apollo_cc_library(
    name = "drivers-sample-canbus",
    hdrs = ["sample-canbus.h"],
    srcs = ["sample-canbus.cc"],
    deps = ["//can_card:sample_can"],
)
```

Then compile normally.

#### Packaging a Locally Developed Module and Deploying It to Other Hosts

After finishing local development, developers may need to package the modules developed on the local machine and deploy them to another host. Here, taking the plugin compiled above as an example, we describe how to package and deploy in package management mode.

##### Packaging

buildtool packages modules with the following command:

```shell
buildtool release -p sample_plugin core
```

> The -p parameter specifies the source path of the modules to package. When this parameter is not added, buildtool tries to package all modules in the workspace

After packaging completes, buildtool produces output similar to the following:

```shell
[buildtool] 2023-10-27 19:21:53 INFO update the local cache
[buildtool] 2023-10-27 19:21:53 INFO update complete
[buildtool] 2023-10-27 19:21:53 INFO Reconfigure apollo enviroment setup
[buildtool] 2023-10-27 19:21:53 INFO use src code of planning-task-lane-follow-path in workspace
[buildtool] 2023-10-27 19:21:56 INFO Analyzing dependencies topological graph...
[buildtool] 2023-10-27 19:21:56 INFO building package process started, it will take while...
dpkg-deb: building package 'apollo-neo-sample-plugin' in 'apollo-neo-sample-plugin_9.0.0-alpha2-r28_amd64.deb'.
dpkg-deb: building package 'apollo-neo-core' in 'apollo-neo-core_9.0.0-alpha2-r28_amd64.deb'.
[buildtool] 2023-10-27 19:21:57 INFO Done! Productions is in /apollo_workspace/.deb_local
[buildtool] 2023-10-27 19:21:57 INFO Compress the release files...
[buildtool] 2023-10-27 19:21:57 INFO Release complete, the output files: release.tar.gz
```

A release.tar.gz file is generated in the workspace, which can be used for subsequent deployment on other hosts.

##### Deployment

> Before deployment, make sure the aem tool has been downloaded on the other host so that it can start the Apollo container

First, create a workspace for deployment:

```shell
mkdir deployment_workspace
```

Then copy the release.tar.gz and .env files from the previous step to the new host

Next, start the container through aem in the same way

```shell
cd deployment_workspace && aem start
```

After startup, call buildtool inside the container to deploy the project:

```shell
buildtool deploy -f release.tar.gz
```

In this process, buildtool automatically deploys the sample-plugin and core modules and automatically downloads the required dependencies from the network. Depending on network conditions, this process may take 30-60 minutes.

After deployment, you can start dreamview with the `aem bootstrap start` command, or start planning manually through mainboard, just like in the development environment you used earlier.
