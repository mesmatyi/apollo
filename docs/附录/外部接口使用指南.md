## Overview of How to Call the PNC External Interfaces

In the new version, the PNC interfaces have been optimized and upgraded, and the internal PNC interfaces have been uniformly sorted out and encapsulated. When the interfaces of internal PNC modules are upgraded, the external command interfaces can remain unchanged. Users can customize the HMI, task management module, and so on to call the external interfaces and send commands into PNC as needed to implement functions.

![image.png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image_262ffef.png)

## PNC Interface Call Flow

The external interfaces use the service/client calling method. When calling an external interface, the Client side is responsible for sending the command to the Service side. The Service side parses the command, executes the corresponding business logic, and so on, then passes the processed command to the corresponding PNC component for execution and returns a status value to the Client.

![image (1).png](https://bce.bdstatic.com/doc/Apollo-Homepage-Document/Apollo_Beta_Doc/image%20%281%29_5ee22ed.png)

To call a PNC interface, you first need to determine the command according to the required functionality, register the Client_Wrapper/Client side, fill in the command field information needed to implement the function, and finally send it to the Service side for command processing. Taking the LaneFollowCommand command as an example, the detailed process is as follows:

### Step 1: Register the Client_Wrapper/Client Side

Developers first need to choose a type of client to register, which is responsible for sending the interface information. Apollo provides two client types for developers to choose from

1. client_wrapper (recommended): sends commands to the Service and records the information of the sent commands, which can be viewed in cyber_monitor.

2. client: only sends commands to the Service.

#### Registering the Client_Wrapper Side

```bash
// Register the Node
std::shared_ptr<apollo::cyber::Node> node_ =
      apollo::cyber::CreateNode("demo");
// Register the client to send Command commands; CommandName needs to be determined according to the corresponding Command
std::shared_ptr<
      apollo::common::ClientWrapper<apollo::external_command::LaneFollowCommand,
                                    apollo::external_command::CommandStatus>>
      client_wrapper;
// service_name needs to be determined according to the settings of the corresponding service side
client_wrapper = std::make_shared<apollo::common::ClientWrapper<
      apollo::external_command::LaneFollowCommand, CommandStatus>>(
      node_, service_name);
```

> Note: The Client side and the Service side correspond to each other, and service_name must be determined by checking the configuration files of the Service and Client

#### Registering the Client Side

```bash
// Register the Node
std::shared_ptr<apollo::cyber::Node> node =
      apollo::cyber::CreateNode("demo");
// Register the client to send Command commands; CommandName needs to be determined according to the corresponding Command
std::shared_ptr<
      apollo::cyber::Client<apollo::external_command::LaneFollowCommand,
                            apollo::external_command::CommandStatus>>
      client;
// service_name needs to be determined according to the settings of the corresponding service side
client = node_->CreateClient<apollo::external_command::LaneFollowCommand,
                          CommandStatus>(service_name);
```

> Note: The Client side and the Service side correspond to each other, and service_name must be determined by checking the configuration files of the Service and Client
> After completing the above steps, the Client side registration and configuration are complete.

### Step 2: Fill in the Interface Command Information

Interface commands contain different functional fields, and users implement custom functions by modifying specific fields. Developers first need to fill in the corresponding functional fields according to their needs and complete the interface information content. An example is as follows:

```bash
// Define the Command type
  auto command =
      std::make_shared<apollo::external_command::LaneFollowCommand>();
  // Customize Header information injection as needed
  FillCommandHeader(command);
  // Set way_point to (0, 0) and end_pose to (10, 0), using the vehicle's current position as the starting point by default
  // Customize way_point
  apollo::external_command::Pose way_point;
  way_point.set_x(0.0);
  way_point.set_y(0.0);
  way_point.set_heading(0.0);
  std::vector<apollo::external_command::Pose> way_points;
  way_points.emplace_back(way_point);
  // Customize end Pose
  apollo::external_command::Pose end_pose;
        end_pose.set_x(10.0);
        end_pose.set_y(0.0);
        end_pose.set_heading(0.0);
  // Inject way_point information into the Command
  for (const auto& point : way_points) {
    auto way_point = command->add_way_point();
    way_point->CopyFrom(point);
  }
  // Inject end_pose information into the Command
  command->mutable_end_pose()->CopyFrom(end);
  // Inject targe_speed information into the Command
  double target_speed = 10.0;
  command->set_target_speed(target_speed);
  // ....... other information
  // ....
  // ....
```

After completing the above steps, the filling in of the specific interface command is complete.

### Step 3: The Client_Wrapper/Client Side Sends the Command to the Service Side

After the LaneFollowCommand command has been filled in, the Client_Wrapper/Client side provides the following interface to send the command, and the specific command format can be sent according to needs. An example is as follows:

#### Client_Wrapper Side

```cpp
// Send the Command to the service side
std::cout << "Sending command: " << command->DebugString()
<< std::endl;
// The interface for sending commands is the same for the Client_Wrapper/Client side
auto response = client_wrapper->SendRequest(command);
if (nullptr == response) {
std::cout << "Command sending failed, please check the service is on!\n"
<< std::endl;
} else {
std::cout << "**\*\***Finish sending command.**\*\***\n" << std::endl;
}
```

> Note: Common problem: if there is no response for a long time after SendRequest, consider that the Service side failed to start.

#### Client Side

```bash
// Send the Command to the service side
  std::cout << "Sending command: " << command->DebugString()
            << std::endl;
  // The interface for sending commands is the same for the Client_Wrapper/Client side
  auto response = client->SendRequest(command);
  if (nullptr == response) {
    std::cout << "Command sending failed, please check the service is on!\n"
              << std::endl;
  } else {
    std::cout << "******Finish sending command.******\n" << std::endl;
  }
```

> Note: Common problem: if there is no response for a long time after SendRequest, consider that the Service side failed to start.

After completing the above steps, the sending of the LaneFollowCommand command to the service side is complete

### 1. LaneFollowCommand Interface Command and Function Description

```bash
message LaneFollowCommand {
  optional apollo.common.Header header = 1;
  // Unique identification for command.
  optional int64 command_id = 2 [default = -1];
  // If the start pose is set as the first point of "way_point".
  optional bool is_start_pose_set = 3 [default = false];
  // The points between "start_pose" and "end_pose".
  repeated Pose way_point = 4;
  // End pose of the lane follow command, must be given.
  required Pose end_pose = 5;
  // The lane segments which should not be passed by.
  repeated LaneSegment blacklisted_lane = 6;
  // The road which should not be passed by.
  repeated string blacklisted_road = 7;
  // Expected speed when executing this command. If "target_speed" > maximum
  // speed of the vehicle, use maximum speed of the vehicle instead. If it is
  // not given, the default target speed of system will be used.
  optional double target_speed = 8;
}
```

The LaneFollowCommand command is suitable for scenarios of point-to-point driving along structured roads.

Interface description:

1. header is the basic information of the message, which can be injected by calling the apollo::common::util::FillHeader method.
2. command_id is the command's identifying feature.
3. is_start_pose_set indicates whether the starting point is set. If true, the first routing point is used as the starting point; otherwise the vehicle's current position is used as the starting point.
4. way_point specifies the waypoints.
5. end_pose specifies the end point.
6. blacklisted_lane specifies the list of impassable lanesegments.
7. blacklisted_lane specifies the list of impassable roads.
8. target_speed specifies the cruising speed.

### 5. FreeSpaceCommand Interface Command and Function Description

```bash
message FreeSpaceCommand {
  optional apollo.common.Header header = 1;
  // Unique identification for command.
  optional int64 command_id = 2 [default = -1];
  // Pose of the parking spot.
  required Pose parking_spot_pose = 3;
  // Region where openspace trajectory will be searched. Junction containing
  // "non_drivable_roi" should be contained by "drivable_roi"
  // polygon points should be clockwise if outer polygon can drive.
  // otherwise polygon points should be counter-clockwise if inner polygon can drive
  repeated RoiPolygon non_drivable_roi = 4;
  required RoiPolygon drivable_roi = 5;
  // Expected speed when executing this command. If "target_speed" > maximum
  // speed of the vehicle, use maximum speed of the vehicle instead. If it is
  // not given, the default target speed of system will be used.
  optional double target_speed = 6;
}
```

The FreeSpaceCommand command is suitable for scenarios of vehicle driving on unstructured roads

Interface description:

1. header is the basic information of the message, which can be injected by calling the apollo::common::util::FillHeader method.
2. command_id is the command's identifying feature.
3. parking_spot_pose: the stopping point.
4. non_drivable_roi: the set of corner points of the non-drivable area. The corner points need to be given clockwise, and they must be contained within the drivable area.
5. drivable_roi: the set of corner points of the drivable area. The corner points need to be given counterclockwise, and the set of drivable area corner points must be provided.
6. target_speed specifies the cruising speed.

### 6. PathFollowCommand Interface Command and Function Description

```bash
message PathFollowCommand {
  optional apollo.common.Header header = 1;
  // Unique identification for command.
  optional int64 command_id = 2 [default = -1];
  // Path point to be followed, a valid path should contain >= 2 points. No lane
  // on the map is followed for this command.
  repeated Point way_point = 3;
  oneof boundary {
    // PathBoundary with left and right boundary.
    PathBoundary path_boundary = 4;
    // Path boundary generated with the distance from center to left and right
    // boundary given.
    BoundaryWithWidth boundary_with_width = 5;
  }
  // Expected speed when executing this command. If "target_speed" > maximum
  // speed of the vehicle, use maximum speed of the vehicle instead. If it is
  // not given, the default target speed of system will be used.
  optional double target_speed = 6;
}
```

The PathFollowCommand command is suitable for scenarios without a map where the vehicle drives along a route given by the user.

Interface description:

header is the command message header, which can be injected by calling the apollo::common::util::FillHeader method.

- command_id: the unique identifier of the command.

- way_point: the coordinate points on the given route.

- boundary: the lateral drivable area of the vehicle, with two optional ways to set it:
  
  - path_boundary: set left and right boundaries for each path point
  - boundary_with_width: set a uniform left and right boundary width for all path points
  
  If boundary is not set, the vehicle width is used by default as the left and right boundaries. In this case, the vehicle cannot go around obstacles it encounters and can only stop.

### 7. SpeedCommand Interface Command and Function Description

```bash
message SpeedCommand {
  optional apollo.common.Header header = 1;
  // Unique identification for command.
  optional int64 command_id = 2 [default = -1];
  oneof linear_speed {
    // Replace the target speed of current motion command with this new target
    // speed.
    double target_speed = 3;
    // Multiple the target speed in current motion command with the factor. The
    // factor should be in range [0, 1.0].
    double target_speed_factor = 4;
    // Restore the default cruise speed.
    bool is_restore_default_cruise_speed = 5 [default = false];
  }
}
```

The SpeedCommand command is suitable for scenarios that impose additional limits on speed.

Interface description:

1. header is the basic information of the message, which can be injected by calling the apollo::common::util::FillHeader method.

2. command_id is the command's identifying feature.

3. linear_speed: the speed.
   
   a. target_speed: the cruising speed, which overrides the previously set cruising speed.
   
   b. target_speed_factor: the cruising speed factor, which replaces the cruising speed with the original cruising speed \* factor.
   
   c. is_restore_default_cruise_speed: a boolean, which defaults to false when target_speed/target_speed_factor is not set; it restores the default cruising speed.
